## Rulings

- The package is `google-colab-cli` ≥ 0.7.1 (current 0.7.5; wheel 83,521 bytes, sdist 1,196,217 bytes), installed with `uv tool install`; the installed command is `colab`. The unofficial `colab-cli` package is never used.
- Login is `--auth oauth2` passed explicitly on every wrapper call; the copy-paste flow is the headless path. The refresh token at `~/.config/colab-cli/token.json` and session state at `~/.config/colab-cli/sessions.json` live canonically outside the repo and are never committed; per the transient-mirror ruling below they are also mirrored into the repo as untracked state for restore after a VM restart. All consent scopes are granted at first login.
- the operator holds Colab Pro with a 500 CU balance; at the measured 0.14–0.24 CU/h for high-RAM CPU, credit burn is not a design constraint. Idle burn is: wrappers stop the session on every exit path.
- Local network measured 2026-10-29 from this VM: TTFB 0.51–0.77 s to GitHub / PyPI / Colab / SEC; the real base-clone payload (codeload tarball of workload-repo `main`, 62,639,307 bytes) downloaded at 2,364,819 B/s in 26.5 s; a generic speed endpoint measured ~2.5 MB/s up and 2.4–2.7 MB/s down. Sync design therefore assumes single-digit MB/s, not broadband. (An earlier probe report of 134,654,898 bytes at 5,369,684 B/s was superseded by the verified re-run with the full command recorded; the design conclusion is unchanged.)
- Code sync is cheap at those rates (the 2026-10-28 snapshot bundle was 46,516,736 bytes — seconds to a minute). Data sync is not: workload-repo `.artifacts` is 6.6 GB, roughly 20–45 minutes one-way if sent whole. Data moves selectively or is regenerated on the Colab VM; it never moves whole by default.
- Bundles for any target that cloned from origin are built on the origin lineage: a snapshot commit whose parent is the current origin tip (`4eaad91e` at plan time) and whose tree equals the local tree being shipped, with byte size and SHA-256 recorded before transfer and verified after.
- `.artifacts` default exclusions from sync-in: `cache` (2.1 GB), `transient` (344 MB), `caches` (210 MB), `run-logs` (194 MB, an output). Largest candidate payloads needing an explicit ruling per job: `filing_catalog` (2.8 GB), `document_acquisition` (562 MB), `metadata` (471 MB). `.venv` (602 MB) never transfers; it is rebuilt remotely.
- Data moves are decided per class by generator and dependency, not by size alone, and every class is a priced tradeoff among three routes (operator ruling, 2026-10-29): transfer the artifact itself ($T_{transfer} = bytes / channel\ rate$, planning rate 2.4 MB/s from the P0 baseline, re-measured in P2); transfer a smaller upstream driver and regenerate remotely; or regenerate from the network ($T_{regen} = requests / 8 + remote\ compute\ time$, the 8 being the repo's own `sec.rate_limit_rps` default — `DEFAULT_RATE_LIMIT_RPS` in `workload_sec/foundation/runtime/settings/sec.py`). Each class is classified as network-generated, compute-generated, or cache/transient (never moved, rebuilds as a side effect), and compute-generated classes record their driver: the smallest upstream artifact from which they regenerate with zero network.
- Worked example, verified from the code: `filing_catalog` is a zero-network pipeline by contract — it materializes an immutable catalog from a finalized Phase 1 metadata snapshot and constructs no HTTP client (proved structurally by its network-isolation test). Its driver is therefore the metadata snapshot: transferring `metadata/snapshots` (471 MB, ~3.3 minutes at the planning rate) and running materialize on Colab's 8 vCPUs reproduces the catalog, versus ~20 minutes to transfer `filing_catalog/snapshots` (2.8 GB) itself, and versus any SEC refetch, of which it needs none. Because catalog publication is immutable and content-addressed, a remotely regenerated catalog is trusted by comparing its snapshot identity to the local one, not by re-transferring it — and the same logic prices the return trip: a derived artifact whose driver is already local is disposable in both directions (pull back its manifest and identity, not its bytes, unless a local consumer needs the bytes themselves).
- Driver table for every major class (XBRL chat's per-class answer, 2026-10-29, grounded in the pipelines' contracts; nearly every class is content-addressed — snapshot IDs, `manifest_sha256` + `logical_fingerprint` — so regenerate-from-driver is verifiable, and `metadata_sync` already documents copy-based multi-machine distribution in which a plan bundle moved to another machine keeps its completed chunks): metadata snapshots (471 MB) are a root fetch — driver is a plan (136 KB of roster plus chunk layout) plus the network at 8 rps, and re-collection is not identity-preserving (SEC data changes daily), so an existing snapshot always transfers and regeneration happens only when freshness is the goal; `filing_catalog` (2.8 GB) regenerates from one metadata snapshot, verified by its content/feature-addressed snapshot names; cohorts (23 MB) regenerate zero-network from a catalog snapshot plus tracked registry definitions, hash-addressed, and also transfer trivially; document cache and `document_acquisition` (2.1 GB / 562 MB) are genuinely SEC bytes whose small driver is `document_planning` (4.8 MB) — for a new acquisition batch only the plans move and workers fetch their disjoint shards under their own rate windows, while an existing cache needed as a run input moves as one bulk transfer of the named working set; XBRL snapshots (2.2 MB) regenerate from tracked corpora plus the code bundle and are trusted when the DAG fingerprint matches, but transfer when serving as a comparison baseline; `run-logs` are leaves (never an input; only a remote run's own new logs travel back); `transient` has no driver and is disposable on both ends. The only genuinely network-bound roots are metadata collection and document acquisition, and for both the plan bundle is the portable artifact.
- Sentinel resolutions (transcribed at their recommended values when the operator directed implementation, 2026-10-29): repo name is `colab-runner`, checked out in the operator's workspace; the local UI is phased (Step 10 stays gated until a real job has run); Colab is compute-only for v1 (only artifacts, logs, and manifests return; code authorship stays on this machine). Repo configs parsed by the repo's own code are JSON, not YAML, so every script runs on the standard library alone with no PyYAML dependency; `workbench.yaml` is the sole YAML file and is never parsed by repo code.
- Network regeneration on Colab additionally requires `SEC_USER_AGENT` in the remote process environment (acquisition fails or goes anonymous without it). Wrappers pass it through with `--env` from the local environment; the value itself is never stored in the repo.
- Small-sample default (operator ruling, 2026-10-29): most current work runs on small samples — the post-reshape seed is 49 filings with a 28.9 MB tree, plus a 16-filing vintage panel — so a default job's payload is the code bundle plus sample-scale inputs only (tens of MB, seconds of transfer). Any bulk `.artifacts` move needs a per-job justification recorded in its data manifest under the generator rule above.
- A killed local CLI is an expected failure, designed for, not an edge case (operator ruling, 2026-10-29): this machine's own history includes detached process trees being reaped mid-run, and the CLI's open timeout bugs (#82, #183) already show local and remote execution decoupling unpredictably. The execution pattern, checkpoint tiers, and recovery path are therefore decided by the kill-matrix probe in Step 6, not assumed. Until that probe reports, the working defaults are: jobs launch detached on the VM (`nohup`, own log and pid file) with the local CLI only starting and polling; the wrapper writes a local run record (job, remote run-id, session name, start time, state) before launch; and every wrapper entry runs an orphan sweep reconciling run records against `colab sessions` — resume polling, pull results, or stop and report. Checkpoints have two tiers with different survival: on-VM checkpoints survive a local CLI kill but not a session loss, so job manifests set an off-VM push-out cadence (download / Drive / git) for anything a session kill must not lose; manifests also set a small chunk granularity and recovery always relaunches the same remote run-id, per the workload-repo precedent (same run-id relaunch skips completed chunks and loses only the in-flight chunk, provided chunk size is small — 16 in the founding run, not the 1000 default; a re-projection recomputes from scratch).
- Tests and checks are first-class compute-bound workloads for Colab, not only pipeline runs (operator ruling, 2026-10-29): `check.py` and pytest scale with workers, and the local `--workers 2` convention is a property of this 2-CPU machine, not of the codebase. On Colab the worker count comes from the remote resource probe (the repo's cgroup-aware `derive_resources()` budgeting), never from copying the local constant, and the runner records local-vs-remote wall time for the same scoped gate so the speedup is measured, not assumed.
- The Colab VM is treated as disposable: no state lives only there, jobs are checkpointed and resumable, and results return as artifacts plus a hash manifest. Code is authored locally; whether code also returns from Colab is an open question.
- Every long execution passes an explicit `--timeout` (default in wrappers: 18000) or uses the `nohup`-on-VM plus poll pattern; the CLI's 30 s silent default is never relied on.
- Transient-mirror rule (operator ruling, 2026-10-29): anything identified as transient — a file, config, or installed state that will not survive a VM restart — is copied into the repo as untracked state (under `state/transient/`, gitignored), and is copied back to its canonical location by two independent triggers: a periodic cron check and every wrapper invocation (restore on entry, capture back to the mirror on exit). The bootstrap and wrappers resolve `uv` by absolute path (`~/.local/bin/uv`) and never assume `/etc`, systemd, PATH, or any canonical location survived a replacement.
- Each transient item carries its own edge-case rules in a tracked registry, `config/transient.json`: canonical path, mirror path, kind, triggers, conflict rule, file permissions, and a post-restore verification. No generic copy-back is applied blindly. Initial registry entries and their rules:
  - `token.json`: newest-wins in both directions (refresh tokens rotate, so an older mirror must never overwrite a fresher canonical file, and a wrapper exit captures a rotated token back to the mirror); permissions `600` on both copies; verification is JSON parse only, contents are never logged or printed.
  - `sessions.json`: restore only if the canonical file is missing; a restored file is treated as stale until `colab sessions` / `colab status` validates it, and dead sessions are pruned rather than trusted.
  - OAuth client config (`~/.colab-cli-oauth-config.json`, if present): newest-wins, `600`, same no-logging rule as the token.
  - The `colab` tool install itself: not file-mirrored; the registry entry is a version pin and its rule is recreate — `uv tool install` from the bootstrap if the command is missing or below the pin.
  - A dedicated Colab SSH key and its `~/.ssh/config` block (only if `colab ssh` is used): key mirrored at `600`; the config block is restored by marker-delimited append-merge, never by overwriting `~/.ssh/config`, and never duplicates a block already present.
  - systemd units and the restore cron itself (if a UI serve or other supervised piece is added): the unit's canonical copy is the tracked template in `ops/`; restore means render, copy, `daemon-reload`, and enable — performed by the cron trigger or an explicit bootstrap, not by ordinary wrapper calls. The wrapper trigger is the backstop for the cron: if the cron registration itself does not survive, the next wrapper use re-registers it from the repo's saved definition.
  - Colab-side (remote) state is a separate registry class whose rule is recreate, not restore: sessions, remote clones, and remote installs are rebuilt by the remote bootstrap, with checkpoints as their only carried state.
- The CLI has no saved-snippet feature; the repo's tracked `snippets/` directory, run via `colab exec -f` / `colab run`, is the snippet library.

Finally, run the comparative gate: the same scoped `check.py` invocation (a fixed path set) locally with `--workers 2` and remotely with the worker count from the resource probe, recording both wall times and both verdicts.

Kill matrix (`probes/p3_kill_matrix.py`), the core of this step: a deterministic 5-minute job (timestamped heartbeat log, one hashed output per minute, a checkpoint file updated per unit) is run under three launch patterns — (a) a long `colab exec`, (b) `colab run`, (c) detached `nohup` launched by a short `exec` — and subjected, one cell at a time, to: SIGINT to the CLI, SIGTERM, SIGKILL (`kill -9`) of the CLI, killing the wrapper so the CLI is orphaned, letting the CLI `--timeout` expire mid-job, and `colab stop` of the session from a second shell mid-job. Each cell records: whether the remote job was still running, completed, or dead when checked 60 s later; whether a fresh CLI invocation could observe it (`status`, heartbeat log, `sessions`) and retrieve its outputs; whether the session kept burning CU after the kill and for how long; output and checkpoint integrity by hash; and, for SIGINT, whether the interrupt reached the kernel or merely detached locally. Adjacent fault cells: kill the CLI mid-`upload` and mid-`download` (partial-file detection by hash and clean retry), and kill during bundle apply (idempotent re-apply). No cell's outcome is assumed from documentation — including the documented hint from issue #82 that remote execution continues independently of a timed-out local CLI, which the matrix verifies or refutes per pattern.
Low-tier limit probes (`probes/p3_oom_lowtier.py`, operator ruling, 2026-10-29): the OOM loop's purpose is to determine edge cases in the Colab runtime itself — how the runtime fails, reports, and recovers at its limits — and it runs on Colab only, never on this machine — the ramp and BERT snippets (`snippets/memory_ramp.py`, `snippets/bert_batch_ramp.py`) enforce this via `snippets/_remote_guard.py`, refusing to run without a Colab runtime marker (a deliberate local dry run needs `--force-local` and is capped). Limit behaviour is probed on the cheap standard CPU tier (2 vCPU / ~13 GB, ~0.07 CU/h), not on high-RAM — ceilings there are reached quickly and cheaply, and filling ~51 GB just to force an OOM wastes time and units. Two workloads: a synthetic memory ramp (allocate in fixed steps, recording RSS and cgroup readings until the kernel or process dies) and a realistic one — download a BERT-level model from HuggingFace (`bert-base-uncased` class, via `transformers`) and run inference/training forward passes at doubling batch sizes until OOM, recording per-batch memory, the batch size at death, HuggingFace download time and cache size on the ephemeral disk, and what survives each failure (kernel death vs session survival, what `colab status` reports, whether the session is reusable without restart). The same BERT ramp is the control that tells a job's manifest whether its memory model is honest: a workload whose measured ceiling contradicts the `derive_resources()` budget it would be given is flagged before it ever runs on the high-RAM tier. An optional single confirmation run of the ramp's final step on the high-RAM tier checks that the ceiling scales with the shape and the failure mode is the same.
files: `probes/p3_execution.py`, `probes/p3_kill_matrix.py`, `probes/p3_oom_lowtier.py`, `snippets/smoke_duckdb.py`, `snippets/bootstrap_remote.py`, `snippets/heartbeat_job.py`, `snippets/bert_batch_ramp.py`

### Step 8 — Job runner and snippet library

`jobs/<name>/job.yaml` manifest: script or snippet name, profile, bundle/data inputs, remote bootstrap snippet, timeout, checkpoint cadence, expected outputs. Two job kinds are supported from the start: pipeline jobs and gate jobs — a gate job (`bin/colab-check <paths>`) ships the current tree by bundle, runs `check.py <paths>` remotely with the probed worker count, and returns the verdict plus wall time, with no data payload beyond the bundle. `bin/colab-run <name>`: orphan sweep (reconcile run records against live sessions; recover, report, or stop anything a previous kill left behind) → sync in (Step 7) → new session on the profile → write the run record → remote bootstrap → execute in the launch pattern the kill matrix selected as default (detached, unless the matrix proved a tied pattern survives the kills that matter) → poll, pushing checkpoints off-VM at the manifest's cadence → pull results → record `colab usage` before/after → stop session. A separate recovery entry, invoked by the sweep or directly, relaunches a dead job under the same remote run-id so completed chunks are skipped, never re-projected. Seed `snippets/` with `bootstrap_remote.py`, `probe_resources.py`, and `smoke_duckdb.py` from the probes, each runnable standalone via `colab exec -f`.
files: `bin/colab-run`, `bin/colab-check`, `jobs/`, `snippets/bootstrap_remote.py`, `snippets/probe_resources.py`, `snippets/smoke_duckdb.py`
verify: a sample job built from the P3 smoke workload runs end-to-end through `bin/colab-run` and its returned hashes match a local reference run
done when: one named job completes through the runner with a usage delta recorded

### Step 9 — Restart-survival verification

Local leg: simulate a VM replacement's effects — PATH stripped, `colab` tool removed, canonical `token.json` / `sessions.json` deleted, the restore cron's registration dropped, and a wrapper plus its CLI killed mid-job (per the Step 6 matrix) so the next invocation's orphan sweep must find the run record and recover or cleanly close out that job — then prove both restore triggers independently: (a) the next wrapper invocation restores every registry item from the untracked mirror in the repo (and re-registers the cron), with no re-login; (b) with the wrappers untouched, the cron trigger alone restores the same state. Include the conflict edge cases: a canonical file newer than its mirror is never clobbered, and a stale restored `sessions.json` is validated and pruned, not trusted. Colab leg: start a checkpointed job, stop the session mid-run, start a fresh session, and confirm the runner resumes from the last checkpoint and produces the same final hashes as an uninterrupted run. Record both legs; any leg that needs a human action names that action as a documented interaction, not a failure.
files: `probes/p4_restart.py`, `README.md`
verify: both legs recorded with pass/fail; restored files are hash-equal to their mirrors at the correct permissions; the resume leg's final output hashes equal the uninterrupted run's
done when: survival is proven on both legs or the exact human interaction each leg needs is documented in the README
