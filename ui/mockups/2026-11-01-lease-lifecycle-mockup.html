Colab Lease — lifecycle & UI mockup

The rebuild spec for the lease panel: the lifecycle as designed, the requirements as originally stated, and the UI as it should look. Mockup for approval, 2026-11-01. Built from the workbench olive primitives — the same tokens the shipped page uses.

Findings — where the current build diverges

  • The companion server has no supervisor. It is a hand-started process; the runtime restart this morning killed it, and the Library panel answered “Lease server unreachable” (the screenshot that prompted this mockup). Lease enforcement never depended on the server — the reaper holds the deadline — but the manual control surface stayed down until someone restarted it by hand. That is a fundamentals gap, not a UI bug.
  • The artifact was never verified end-to-end. Its build audit failed: the control surface was implemented but never visually verified against live state. What shipped to the phone was the degraded shell.
  • State reads ride a stall-prone channel. Colab file transfers can hang indefinitely on the egress proxy’s IPv4 endpoint. The reads and the keepalive launch are now bounded (10 s / 30 s + 90 s, landed 2026-11-01), so a stall degrades instead of wedging — but the rebuild must treat channel stalls as a normal condition, not an exception.
  • The keepalive launch defect chained. An unbounded, raising launch failed an acquire after its lease already existed, failed the reaper, and starved the kernel pulse. Fixed; the rebuild keeps “launches never raise” as a contract, not a patch.
  • Two surfaces, no drift control. The localhost page and the Library artifact share one frontend and one companion server; the deploy script is manual and nothing detects drift between them.

1 · The system and its primitives

The backend does the work; every surface is a consumer. No agent operates any of this.

Lease core

sync/lease.py via bin/colab-lease. Owns all lifecycle logic and derivation: acquire-or-adopt, budget guard, reap, standing duty, auto-acquire, and the single state read every surface renders.

Companion server

ui/server.py on 127.0.0.1:8793. Thin: shells to the core, serves state, and is the single writer of the outbox. Must be supervised (decision D1) — today it is not, which is finding F1.

Reaper hook

Script-level, every 120 s, no agent: transient restore → reap (deadlines, keepalive, pulses) → auto-acquire → standing duty. Wakes the chat only on actions and failures.

Keepalive loop

Detached on the VM: a heartbeat line every 60 s. Proof the runtime is touched, not proof it survives — lease #2 died with a perfect heartbeat.

Kernel pulse

A trivial exec in the session’s kernel every 600 s, driven by the reaper. The second survival channel; a timed-out pulse reads as busy, not failed.

Spec catalog

config/profiles.json: every grantable tier with its measured CU/h rate. An unmeasured rate is null and renders “cost unconfirmed” — never priced by invention, and the budget guard projects nothing for it.

Budget guard

Every acquire is priced before it runs: projected cost vs the daily/monthly caps (10 / 100 CU) and the standing sub-cap (2 CU/day for the lobby). Refusal is a result, not an error.

Demand & grant files

var/lease-request.json — any thread plants a demand; the auto duty consumes it when a lease stands. var/grant.json — a two-tier window the standing duty maintains.

Outbox & notify hook

Every start, stop, and grant is appended to var/ui-outbox.jsonl by the companion server and announced to the main chat by the notify hook — so other threads learn a lease is up and can tap into it.

Surfaces

The Library artifact (phone) and the localhost page render the same frontend from the same served state. Countdown arithmetic on served timestamps is the one client-side derivation.

Transient mirror

Login token, session bindings, and tool install are mirrored into the repo as untracked state and restored by the hook and every wrapper — nothing the lease needs dies with a VM restart.

Colab session

The leased VM itself: one per profile, treated as a machine — code arrives by snapshot bundle, work runs detached, only artifacts and logs return.

2 · The lifecycle

One lease

StartTap in the panel · a planted demand (auto on) · the standing duty
→
Budget guardProjected cost priced against the caps before anything is created
→
AcquiringSession created (one approval, front-loaded per host) or the live lease adopted
→
ActiveRecord written with a hard end time — the window chosen at the tap, from 1 h to 3 days
→
ReleasedDeadline · manual stop · grant expiry (standing leases)
While active, the reaper cycles every 120 s: heartbeat stale → relaunch the keepalive (bounded, never raising) · pulse due → pulse the kernel · session unreadable → keep the record (unknown is never read as dead) · confirmed gone → clear the record.

A duration is a window, not a single session. No Colab session outlives the platform’s 12 h cap, so a window longer than one session is maintained the way the standing lobby already is: the reaper renews the session at the cap (or on death) under the same end time, and the budget guard prices the whole window at the tap. The picker offers 1, 2, 4, 8, 12, 16, 24 hours, 1, 2, 3 days, and a custom hours value — for grants as well as normal leases. What this changes in the current fundamentals is decision D5.

Refused — budgetProjection over a cap. Nothing is created; the refusal is the result.
Launch-failed (keepalive)A result, not a crash: the lease stands, the pulse still fires, the next cycle retries.
Kept — unknownThe sessions list can’t be read. The record stays; a lease is forgotten only on confirmed absence or a successful stop.

3 · As originally described

The requirements this design answers, in the order they were set down. Paraphrased rulings, not quotes.

  • 2026-10-29 — the setup. A Colab Pro plan (500 credits) is compute this machine can’t match (2 vCPU here; the high-RAM tier is 8 vCPU / ~55 GB). The runner is its own repo, fundamentals first: login, a UI if one is made, saved snippets (the repo’s tracked snippet library, since the CLI has none), and survival of VM restarts on both machines — anything transient is mirrored into the repo and restored by script.
  • 2026-10-29 — one lease. One shared session per profile, treated as a VM, up to 8 hours, approved once; all work shares it; it is shut down when unused — with idle shutdown off by default, because the XBRL work may claim it at any time.
  • 2026-10-30 — survival channels. An idle runtime dies; a keepalive loop holds it. When a lease died anyway with its heartbeats perfect, a second channel was added: the kernel pulse.
  • 2026-10-31 — no agent in the loop. Once set up, everything is scripted. The UI is like the workbench: a tap starts a lease, the duration is chosen at the tap, early termination is one tap — the operator is the manual control. Starts and stops notify the main thread so other threads can use the lease.
  • 2026-10-31 — the standing tier. The low tier is kept alive as long as possible so there is no tap every time; future tasks tap into it when it is up. It is a different cost scenario with its own configuration — hence the sub-cap.
  • 2026-10-31 — parallel build. UI and two-tier core are built in parallel where the contracts are known, not sequentially.
  • 2026-11-01 — any spec, priced. The UI grants any available tier or spec with its cost shown — never one hardcoded spec. An unmeasured cost is shown as unconfirmed.
  • 2026-11-01 — reachable. The panel must be openable from his phone: a deploy script to the artifacts library, not a localhost-only page.

Decisions

D1 — Companion supervision. The server must come back by itself after a restart (finding F1). Recommendation: a script-level watchdog in the reaper hook’s family — probe 8793 each cycle, restart via ui/ui.sh, announce only when it restarts something. A systemd unit is the wrong tool here: units don’t survive this machine’s restarts, and the hook pattern is already proven.
D2 — “Restart lease server” in Panel D. The degraded panel offers the restart as a tap (it runs ui/ui.sh start, nothing more). Recommendation: ship it — the panel is the manual control surface, and a dead server shouldn’t need a chat round-trip. Shown in the mock; rule on it here.
D3 — One surface or two. Recommendation: the Library artifact is the panel; the localhost page stays as a debug surface running the same frontend, and ui/deploy.sh gains a drift check so the two can’t silently diverge.
D4 — Warm-on-renew. A renewed lobby can be made work-ready automatically (bundle + env build, ~35 s) instead of merely marked warm: pending. Recommendation: defer it — the lifecycle marks the hook point; the standing lease is useful unwarm­ed, and warming is its own build.
D5 — Durations past one session (exception, needs a ruling). The picker now offers up to 3 days, but two current limits stand in the way: the config caps a lease at 8 h (the 2026-10-29 ruling), and the platform caps any single session at 12 h. A 16 h–3 d duration can therefore only exist as a window the reaper maintains by renewing the session — the standing lobby’s mechanism, generalized to normal leases. Recommendation: adopt the window semantics (the per-session cap rises to the platform’s 12 h; the end time chosen at the tap is what’s enforced and priced). The alternative is capping the picker at 12 h — the mock shows the full set, so rule here before the rebuild prices it.
